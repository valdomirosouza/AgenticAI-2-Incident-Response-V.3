# Spec 15: Supply Chain Policy

**Domain**: security
**Owner**: Security Lead
**Status**: Approved
**Date**: 2026-05-17
**Issue**: #12
**Linked ADRs**: ADR-0019, ADR-0022
**Review cadence**: Every release + on CVE event

---

## 1. Purpose

Define the SBOM format, dependency pinning rules, CVE triage SLA, license allowlist and
artifact provenance requirements that govern all software components in the Copilot.

---

## 2. Context

ADR-0019 adopted CycloneDX v1.6 SBOM generated by Syft on every build, with Grype CVE
scanning as a PR gate. ADR-0022 adopted pip-compile hash pinning for Python dependencies
and SHA pinning for GitHub Actions. This spec translates both into operational policy:
what is pinned, what is allowed, how CVEs are triaged and what evidence is required for
SLSA Level 2 compliance.

---

## 3. Decision

### 3.1 SBOM specification

| Property    | Value                                                                           |
| ----------- | ------------------------------------------------------------------------------- |
| Format      | CycloneDX v1.6 JSON                                                             |
| Generator   | Syft (latest pinned SHA in CI)                                                  |
| Trigger     | Every PR (attached as artifact) + every release (published to GitHub Release)   |
| Contents    | All Python packages, system packages in Docker image, GitHub Actions used       |
| Retention   | PR artifacts: 90 days; Release artifacts: release lifetime + 2 years (ADR-0030) |
| Attestation | SLSA provenance attestation generated alongside SBOM on release builds          |

SBOM is attached to the GitHub Release and referenced in `SECURITY.md` for public
transparency (SLSA Level 2 requirement).

### 3.2 Dependency pinning rules

#### Python packages (`requirements.in` → `requirements.lock`)

```
# requirements.in — abstract dependencies (human-maintained)
microsoft-presidio>=2.2
opentelemetry-sdk>=1.20
anthropic>=0.25
pydantic>=2.0

# requirements.lock — concrete pins with hashes (generated by pip-compile)
microsoft-presidio==2.2.354 \
    --hash=sha256:abc123... \
    --hash=sha256:def456...
```

- `requirements.in` is committed. `requirements.lock` is generated and committed.
- `pip install --require-hashes -r requirements.lock` is used in all Docker builds.
- No `requirements.txt` without hashes is accepted — Semgrep gate `no-unpinned-deps` blocks it.
- Dependabot is configured to open PRs for `requirements.in` updates weekly.

#### Docker base images

```dockerfile
# CORRECT — pinned by digest
FROM python:3.12-slim@sha256:a1b2c3d4...

# PROHIBITED — floating tag
FROM python:3.12-slim
```

Digest pinning is enforced by the `docker-unpinned-base` Checkov rule (ADR-0017 G05).

#### GitHub Actions

```yaml
# CORRECT — pinned by SHA
- uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2

# PROHIBITED — floating tag
- uses: actions/checkout@v4
```

All GitHub Actions must be pinned to a full commit SHA. The SHA-to-tag mapping is
documented in a comment on the same line. Enforced by Semgrep rule `actions-unpinned`.

### 3.3 CVE triage SLA

| CVSS score | Severity    | SLA from discovery         | Action required                                      |
| ---------- | ----------- | -------------------------- | ---------------------------------------------------- |
| 9.0 – 10.0 | Critical    | **24 hours**               | Patch or remove dependency; PR merged before SLA     |
| 7.0 – 8.9  | High        | **5 business days**        | Patch or accepted-risk entry with Tech Lead sign-off |
| 4.0 – 6.9  | Medium      | **30 days**                | Scheduled update in next sprint                      |
| 0.1 – 3.9  | Low         | Next release (best effort) | Batch update acceptable                              |
| 0.0        | None / Info | No obligation              | —                                                    |

An "accepted risk" entry for High CVEs requires:

1. Written justification: why the vulnerable code path is not reachable in this deployment.
2. Tech Lead sign-off recorded in the GitHub Security advisory.
3. Re-evaluated at every subsequent release until patched.

Critical CVEs have no accepted-risk path — they must be patched within 24 hours or the
affected component must be removed from the build.

### 3.4 CVE scanning gates

| Gate    | Tool  | Trigger                 | Threshold                                  |
| ------- | ----- | ----------------------- | ------------------------------------------ |
| G07     | Grype | Every PR                | Zero Critical CVEs                         |
| G14     | Trivy | Every PR (Docker image) | Zero Critical CVEs in base image           |
| Release | Grype | Release gate            | Zero Critical + zero unmitigated High CVEs |
| Release | Trivy | Release gate            | Zero Critical in production image          |

Grype and Trivy databases are updated before each scan run (no stale DB accepted).

### 3.5 License allowlist

Only dependencies with the following licenses are permitted without additional review:

| License                    | SPDX identifier | Notes                                      |
| -------------------------- | --------------- | ------------------------------------------ |
| MIT License                | MIT             | Permissive; no restrictions                |
| Apache License 2.0         | Apache-2.0      | Permissive; patent grant included          |
| BSD 2-Clause               | BSD-2-Clause    | Permissive                                 |
| BSD 3-Clause               | BSD-3-Clause    | Permissive                                 |
| Python Software Foundation | PSF-2.0         | Python standard library components         |
| ISC License                | ISC             | Permissive; functionally equivalent to MIT |
| Mozilla Public License 2.0 | MPL-2.0         | Weak copyleft; file-level only             |

**Requires Tech Lead review before use:**

| License      | SPDX identifier    | Reason                                              |
| ------------ | ------------------ | --------------------------------------------------- |
| LGPL v2 / v3 | LGPL-2.0, LGPL-3.0 | Weak copyleft; dynamic linking usually safe         |
| CC-BY 4.0    | CC-BY-4.0          | Data/docs licenses; verify attribution requirements |

**Prohibited:**

| License                 | SPDX identifier  | Reason                                         |
| ----------------------- | ---------------- | ---------------------------------------------- |
| GPL v2 / v3             | GPL-2.0, GPL-3.0 | Strong copyleft; taints entire codebase        |
| AGPL v3                 | AGPL-3.0         | Network copyleft; incompatible with SaaS model |
| SSPL                    | SSPL-1.0         | Service-side copyleft (MongoDB licence)        |
| Commons Clause addendum | —                | Restricts commercial use                       |
| Unlicensed / no licence | UNLICENSED       | No usage rights granted                        |

License scanning is performed by `pip-licenses` on every PR and reported as a CI
annotation. Prohibited licenses block merge (G03 Semgrep `prohibited-license` rule).

### 3.6 SLSA Level 2 compliance evidence

| SLSA requirement                 | Evidence                                                         |
| -------------------------------- | ---------------------------------------------------------------- |
| Versioned source                 | Git tag on every release (`v<semver>`)                           |
| Build service                    | GitHub Actions (tamper-evident logs)                             |
| Authenticated build              | GitHub OIDC token — no static build credentials                  |
| Provenance available             | SLSA provenance attestation generated by `slsa-github-generator` |
| Provenance includes build params | SBOM + provenance reference build SHA, workflow, trigger         |
| Isolated build                   | GitHub-hosted runner (ephemeral); no self-hosted runners         |

SLSA provenance attestation is uploaded to the GitHub Release alongside the SBOM and
can be verified with `slsa-verifier`.

### 3.7 Dependency update cadence

| Update type                      | Frequency  | Automation             | Owner            |
| -------------------------------- | ---------- | ---------------------- | ---------------- |
| Security patches (Critical/High) | Within SLA | Dependabot PR + manual | Tech Lead        |
| Minor/patch updates              | Weekly     | Dependabot PRs         | Engineering Lead |
| Major version upgrades           | Quarterly  | Manual assessment      | Tech Lead        |
| GitHub Actions SHAs              | Monthly    | Dependabot (actions)   | Engineering Lead |
| Docker base image digest         | Weekly     | Dependabot (Docker)    | Engineering Lead |

## 4. Acceptance Criteria

- [ ] SBOM spec defines format (CycloneDX v1.6), generator (Syft), trigger and retention
- [ ] Python pinning shows `requirements.in` → `requirements.lock` with hash example
- [ ] Docker image and GitHub Actions pinning rules with prohibited floating-tag examples
- [ ] CVE triage SLA: Critical = 24h, High = 5 business days, Medium = 30 days
- [ ] Critical CVEs have no accepted-risk path (patch or remove only)
- [ ] License allowlist explicitly lists permitted, review-required and prohibited licenses
- [ ] SLSA Level 2 evidence table covers all 6 requirements
- [ ] Language: English only (RULE-005)
