# ADR-0010: Blameless Post-Mortem as Mandatory Retrospective Format

**Status**: Accepted
**Date**: 2026-05-17
**Deciders**: Valdomiro de Oliveira Souza Júnior (Tech Lead / Researcher)
**Affected RQs**: RQ2 (MTTD/MTTR improvement), RQ3 (learning loop), RQ4 (compliance)

---

## Context

Post-mortems are a primary input to the Copilot's learning loop: the PostMortemAgent
synthesises incident timelines, and the resulting structured documents feed back into
the runbook store and the RCA knowledge base. The quality and consistency of post-mortem
documents directly affects the quality of future triage and RCA outputs.

Two problems motivate this decision:

1. **Blame-oriented retrospectives produce low-quality learning data.** When individuals
   are blamed, teams under-report contributing factors, timeline details are omitted, and
   the root cause is attributed to human error rather than the systemic conditions that
   allowed the error to occur. This produces post-mortem documents that are useless for
   ML-based pattern recognition.
2. **Inconsistent format produces unstructured data** that the PostMortemAgent cannot
   parse reliably without expensive free-text extraction. A mandatory structured template
   ensures machine-parseable output from the first document.

ITIL 4 Problem Management defines post-incident review as a required practice for
continual improvement. The blameless variant is the standard adopted by Google SRE
(Beyer et al., 2016) and is consistent with psychological safety research (Edmondson, 1999).

## Decision

All incident post-mortems in this project — both those generated by the PostMortemAgent
and those authored manually — must follow the **Blameless Post-Mortem** format defined below.

### Mandatory format

Every post-mortem document is stored in `docs/post-mortems/YYYY-MM-DD-<incident-id>.md`
and must contain all eight sections:

```markdown
# Post-Mortem: <incident-id> — <one-line summary>

**Date**: YYYY-MM-DD
**Duration**: HH:MM (detection to resolution)
**Severity**: P1 / P2 / P3
**MTTD**: X min | **MTTR**: X min
**Authors**: [names or roles]
**Status**: Draft | Reviewed | Closed

---

## 1. Impact

[What was affected: services, users, CUJs, SLO consumption]

## 2. Timeline

| Time (UTC) | Event | Actor (human or agent) |
| ---------- | ----- | ---------------------- |
| HH:MM      |       |                        |

## 3. Root Cause

[The specific condition(s) that caused the incident — systems and processes, not people]

## 4. Contributing Factors

[Conditions that increased the likelihood or severity — always systemic, never personal]

## 5. Detection

[How and when the incident was detected. Was MTTD within SLO?]

## 6. Resolution

[What actions resolved the incident. Which were taken by the Copilot vs. humans?]

## 7. Action Items

| Action | Owner (role) | Due date | Issue |
| ------ | ------------ | -------- | ----- |
|        |              |          |       |

## 8. Lessons Learned

[What the system and team learned. How does this change runbooks, alerts or guardrails?]
```

### Blamelessness rules (enforced by PostMortemAgent output filter)

- **Prohibited:** individual names in Root Cause or Contributing Factors sections.
- **Prohibited:** language attributing failure to personal error, negligence or skill.
- **Required:** every root cause statement references a system, process or configuration.
- **Required:** action items target systems, processes or documentation — never individuals.
- **PII rule:** all names in the Timeline `Actor` column must be replaced with role
  labels (`on-call-engineer`, `incident-commander`) before storage (RULE-C03, GDPR Art. 25).

### MTTD and MTTR recording

Every post-mortem records MTTD and MTTR in the header. These values feed the evaluation
dashboard (issue #11) and constitute the primary quantitative evidence for the dissertation
(CLAUDE.md §1.6 criterion 1, RULE-003).

## Alternatives Considered

| Alternative                                | Pros                                                                                                | Cons                                                                                                  |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| **Blame-oriented RCA**                     | Identifies specific human decisions                                                                 | Produces low-quality, incomplete data; harms psychological safety; useless for ML pattern recognition |
| **Free-form narrative**                    | Low authoring friction                                                                              | Unstructured; PostMortemAgent cannot parse reliably; MTTD/MTTR not captured consistently              |
| **Root Cause Analysis only (no timeline)** | Faster to write                                                                                     | Timeline is the primary ML training signal; omitting it cripples the learning loop                    |
| **Blameless structured post-mortem** ✅    | High-quality ML training data; psychological safety; consistent MTTD/MTTR capture; ITIL 4 compliant | Mandatory 8-section structure adds authoring time — mitigated by PostMortemAgent draft generation     |

## Consequences

**Positive:**

- PostMortemAgent-generated drafts are machine-parseable by construction — the structured
  template is both the human document and the ML training record.
- MTTD and MTTR captured in every post-mortem header — direct input to the dissertation
  evaluation metrics (RULE-002: quantitative evidence required).
- Blameless format produces complete timelines and contributing factors — higher-quality
  RCA training data for future model fine-tuning.
- PII scrubbing rule (role labels instead of names) satisfies GDPR Art. 25
  (Privacy by Design) and RULE-C03.
- ITIL 4 Problem Management compliance: structured retrospective with action items and
  owner roles.

**Negative / Trade-offs:**

- 8-section mandatory format may feel heavyweight for minor (P3) incidents — consider
  a simplified 4-section lightweight template for P3 as a future extension.
- PostMortemAgent must implement the PII scrubber for names in the Timeline section
  before any post-mortem is stored — dependency on `src/guardrails/pii_sanitizer.py`.

## Review Criteria

Revisit this decision if:

- PostMortemAgent draft quality is low (human editors rewrite > 50% of content) —
  revisit the template structure to better match LLM generation patterns.
- A P3 lightweight template is needed — create a complementary spec without changing
  this format for P1/P2 incidents.
- ANPD or legal review requires changes to the PII handling in the Timeline section.
